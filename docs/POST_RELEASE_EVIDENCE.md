# 灰度发布后的人工证据追踪与自动回滚

## 为什么要做

之前系统可以用当前人工标注统计灰度规则的误报/漏报，并在人工确认退化后自动回滚，但没有明确区分**发布前已经知道的问题**与**本次上线后新复核的帖子**；相邻灰度也可能因为上一轮新近的监控快照而推迟当前首次巡检。

本轮新增一个与发布实例绑定的只读 `postReleaseEvidenceReport`，同时保留现有全量人工标签退化保护。不会自动放大灰度，也不会因为“没有找到新问题”就宣布成功。

## 证据边界与指标

- 从 `real_problem_production_release` 读取**当前最新发布事件**、提交时刻与发布前验收 evidenceHash，通过 `real_problem_release_preflight` 查找匹配版本，显示冻结回归样本版本、冻结样本指纹、冻结后人工新标注指纹及来源级签收指纹。旧式记录缺失时明确显示“不能核对基线”，而不是猜测发布版本。
- 只读取最多400条 `new/saved` 的 HTTPS 来源，按 `sourceId` 去重。必须实际落入本次灰度稳定 hash 桶，才进入“受控桶”；只在基础判定和当前灰度判定出现差异时才计算该规则对这些帖子造成的分类变化。
- 只把人工 `discovery_quality_labels.at` **严格晚于本次发布事件时间**、与当前原帖 revision 匹配、明确为 `real_problem` 或 `not_problem` 的标签纳入“发布后新复核”。没有时间、过期、未确认以及发布前标签单独计数，不能当成已验证质量。
- 在被曝露且改变判定的帖子上，区分新增漏报、误报、去除的误报和救回的正例；只显示最多20条案例详情，来源维度最多30个域名。所有日志和 API 均不公开冻结集中的完整历史原帖正文。

**注意**：标签在发布后被复核，不代表原帖首次发表于发布后；同一用户在两个论坛发布也可能是两条帖子。系统不验证作者身份或付费需求。人工选择性标注无法外推生产总体精确率/召回率。

## 自动回滚和巡检

- 现有 `captureProductionMonitor` 每次保留全量标注对照，另行记录**本次发布**的后验数据、版本基线、证据指纹及结论。
- 在人工已确认的灰度桶中出现至少一条新增漏报或新增误报，或现有全部人工标注对照发现退化时，**事务内自动回滚基线**并写入监控历史与审计事件。人工显式回滚不受本功能阻碍。
- `createProductionGuard` 保留原有每分钟检查、约每15分钟捕获快照的轮询约定；现在若最近监控快照 `releaseRevision` 不等于当前发布版本，**立即进行本次发布的首次快照**，避免继承上个灰度周期的“刚检查过”状态。原有审批撤销检测仍优先触发回滚。
- 自动巡检为**进程内**定时任务，需要服务器正常运行；它不是一个可靠的外部分布式告警系统。发生进程宕机、网络阻塞或数据库不可用时无法保证立刻回滚，真实部署需要另行监控。
- 存在发布记录但找不到匹配的发布前证据时，界面明确标记“发布基线不能核实”，不会伪称正常；旧版灰度兼容、原有回滚仍可用。

## 入口与接口

入口：**机会简报 → 信息源与信号 → 信息源质量反馈 → 灰度后证据与回滚**。

`GET /api/discovery/post-release-evidence`：走原有 Owner 鉴权，返回只读 `report`、最多12次监控历史摘要。显示发布状态、具体发布前证据、发布后受控新复核计数、可能的已知退化、证据指纹和回滚历史。这是观察页面，不会直接改变规则；真正回滚仍由现有监控事务、自动巡检或 Owner 按钮执行。

## 验收

使用独立 SQLite 的合成样本覆盖：发布前与发布后标签区分、原帖变更导致标签失效、不属于灰度桶的人工标签不得错误归因、哈希桶受控且有新增误报/漏报时自动回滚、每次新发布第一次巡检不被前一轮快照阻碍、HTTP Owner 鉴权与只读、Chromium 空状态面板。

发布状态 `no_known_post_release_regression` 只表示这部分已复核样本中没有发现退化，不构成真实准确率上升证明；`awaiting_post_release_review` 应优先推动人工查验，而非扩大灰度。

此 PR 仅是代码和测试，不能证明生产服务已经部署或生产环境已完成实际审核。
