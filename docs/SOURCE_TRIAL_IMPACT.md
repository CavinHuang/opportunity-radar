# 生产规则来源级离线核查（Owner 签收 / 1–5% 灰度保护）

## 背景与设计边界

当前 Radar 具有 `real_problem_v1` 基础判定、离线规则试验、人工批准、影子评估、发布前核查，以及 1–5% 生产灰度。先前的离线报告主要汇总全部人工标签的变化，却不能直观确认**某条来源的具体帖子**会受到新策略影响，也不能保证受影响帖子已经由 Owner 核对。于是本轮新增来源级影响清单，且把该清单的人工签收列为发布前和生产灰度的**必要条件**。

不改变分类规则或线上候选排序。**本项目只允许 `require_workaround` 这一个更严格的变体进入当前灰度；`review_promotion_block` 仅供离线对照，不会被允许上线**。

## 离线比较的口径

- 读取最多 400 条 `new/saved`、具有标题和 HTTPS URL 的帖子，与当前机会扫描保持一致；逐条同时计算 `assessRealProblem` 基础规则和指定离线策略的原帖资格。
- 一致的来源 `revision` / 标签 `sourceRevision` 才能计入人工真值。来源编辑、`uncertain` 和未审核的标签**不可当成问题或非问题**。
- 按 URL 域名列出变更数、已经人工复核的变更、未复核变更、**新增漏报 / 新增误报 / 减少误报 / 救回正例**；所有变更原帖可打开原文并修改人工标签。
- 这是一份**原帖资格级**对照，既不是榜单前 50 的排名 A/B，也不是流量随机实验。跨域名不等于跨独立用户，选中标注不构成总体正确率。

## Owner 签收条件

必须同时满足：所比较规则确实是唯一允许上线的 `require_workaround`；规则试验已获批准；当前有效人工标签至少 20 条、分布在至少 2 个域名；本次离线策略确实改变了至少 1 条帖子的资格；所有变化的帖子已经人工核对为当前版本；没有在人工样本上造成新增误报或漏报。

只有全部满足，才允许在 **机会简报 → 信息源与信号 → 信息源质量反馈 → 离线规则影响核查** 填写不少于 12 字的复核理由。签收冻结来源、标签、规则审批的完整指纹；任何新帖子、来源内容/标注更新、试验审批变化都会使旧签收失效。签收记录保存在 `discovery_rule_decisions` 现有版本化表中，并记录 Owner 审计事件，不自动触发灰度。

## 发布链路

1. 人工标注正例、反例与有可能被规则影响的原帖；检查是否包含复制、转载或同源假象。
2. 在来源级对照查看每条变更和域名差异；材料不足时继续核查，不能签收。
3. 规则试验审批 → 影子评估 → 来源级签收 → `releasePreflight`。发布前检查与证据指纹现在包含来源级签收状态。
4. 原有 `changeProductionRule` 继续只允许 1–5% 的 Owner 显式灰度申请，并再次验证来源级签收。回滚操作不依赖签收，随时可用；监控中的已标记退化仍自动回滚。

API：`GET /api/discovery/source-trial-audit` 返回 `report/history`；`POST /api/discovery/source-trial-audit` 提交 `{policy_id,fingerprint,expected_revision,reason}`，走现有 Owner 鉴权、Origin、事务与幂等机制。

## 验收与限制

CI 应证明：无来源签收时既不能固定发布前检查，也不能开启灰度；两个来源、20+有效标签、完整受影响核查及无退化时可以人工签收；来源改动、人工标签更改、来源覆盖不足或已知新漏报都会阻断；回滚仍保持可用。所有测试仅在合成数据的独立 SQLite 执行。

人工签收**不是上线证明、不会改善准确率**。真实生产的镜像版本和数据库健康还应通过 `docs/DEPLOY.md` 的只读版本校验、备份和日志验收。成功灰度后的质量报告才是下一次继续/暂停判断的输入，且绝不能推断消费者付款或独立需求已验证。
