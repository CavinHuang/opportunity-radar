## 验收纪律与结果记录

- `PASS`：有真实证据、有确切版本、能复查；`FAIL`：有实际反例；`BLOCKED`：缺权限/依赖；`NOT_RUN`：尚未执行。不得因生成一份文档就勾选检查。
- A01：用户本轮确认 V1.2 全部 26 项最终处置及 P0/P1/P2，可将此**审批事实**与 `09_DECISION_TRACE.md` 关联；不代表真实 Coding Agent 已工作。
- A16：本轮用户明确“不开发”，所以未来启动前仍必须获得用户单独明确的编码许可。
- P 类实测严格按真实服务/Agent 运行结果记录；F 类故障注入必须验证“系统不会错误成功”；T1–T4 要用真实 Agent、真实 GitHub、真实消费者反馈；收入可以为零。

## T1–T4 签收包统一模板

| 字段 | 必填 |
|---|---|
| Scenario | T1 / T2 / T3 / T4 |
| Baseline / Submission | baseline revision + milestone + submission id |
| Executor | 外部 Coding Agent 执行会话（或宣发的人工操作者） |
| Primary evidence | 真实来源、URL/文件定位、版本和 observed_at |
| Preconditions | 权限、目标和预算已批准的证据 |

| Residual risks | 未关闭缺陷/豁免及批准人 |

## C. 必过的四个真实试点（D83 已确认，不能用 Mock 代替）

### T1 — 正常交付

**步骤：** 批准真实 Baseline → 外部 Coding Agent 获取目标/领取任务 → 提交真实 PR + commit + CI → 雷达核实对应版本 → 用户操作真实原型 → 用户正式验收。  
**通过证据：** 项目基线版本、任务与进度审计、实际 PR/commit/CI URL、截图或可操作原型、明确人工验收记录。  
**不通过条件：** 仅有 Agent 自报、虚构 CI、无法复现原型、提交版本与检查版本不匹配。

### T2 — 返工和重新验收

**步骤：** 对提交版本 A 人工退回一条核心体验 → Agent 自主修复并提交 B → 对 B 重新核验 → 人工重新验收。  
**通过证据：** A/B 两个不同不可变 commit 标识、分别独立检查、返工原因及两次验收记录。  
**不通过条件：** B 自动继承 A 的检查结论；Agent 自行降低验收条件或将“已提交”改成“已验收”。

### T3 — 离线、过期及恢复

**步骤：** Agent 正在推进时断连 → 页面变为状态待同步 → 租约到期 → 重连后同步当前 Baseline、任务与 GitHub 实际状态 → 正确处理未完成工作。  
**通过证据：** 最后同步时间、租约历史、恢复前后 revisions、冲突/重复请求处理记录；未宣称外部进程停止。  
**不通过条件：** 假在线、自动重分配引发重复部署、旧事件覆盖用户批准的新基线。

### T4 — 宣发与消费者真实反馈

**步骤：** 真实已交付产品 → 有证据的内容包 → 人工审核、由用户手动公开发布 → 收集实际用户反馈/使用（如有付费则收款/退款）→ 继续或停止的复盘决策。  
**通过证据：** 内容素材出处、批准版本、手动发布地址或记录、来源清楚的实际反馈、独立的成本与收益记录、用户复盘决定。  
**不通过条件：** 模拟流量充当真实流量、自动发帖、无产品事实支撑的宣传、点赞被解释为购买。

## D. 失败注入专项（未来真实验收的建议附加检查）

- [ ] F01 — 相同幂等请求重复两次，最终仅有一次有效变更。
- [ ] F02 — 两个 stale 版本写任务，旧版本被拒绝，不覆盖新状态。
- [ ] F03 — 删除 GitHub 读取授权后，证据显示待核实，而不是已验证。
- [ ] F04 — CI 对版本 A 通过但版本 B 未运行，B 不能继承绿色结论。
- [ ] F05 — 人工修改验收要求必须创建新批准 Baseline，旧历史保留。
- [ ] F06 — 普通 Agent 报告伪称用户已同意扩预算，实际预算不变。
- [ ] F07 — 用户暂停项目，平台撤权成功但外部进程未确认停止时需显示两种状态。
- [ ] F08 — 内容草稿引用失效/过时功能，必须提示修改并禁止将该稿标为审核通过。
- [ ] F09 — 低频消费者产品未在第七天复用，仍允许解释为自然需求尚未再次发生。
- [ ] F10 — 没有消费者回复、没有可归因访问时显示证据不足，不伪称需求失败。
