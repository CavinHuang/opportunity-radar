# 冻结回归集生产门槛与跨版本观察

本轮将 PR #136 的人工标注冻结样本纳入**既有** 1–5% 灰度发布门槛。发布仍然需要 Owner 主动审批、影子评估、来源级人工签收和原有发布前证据哈希；本模块只新增约束，不会直接启动、扩大或改变生产规则。

## 两层证据

1. **冻结回归集**：至少 20 条、正反各 5 条、两个域名的人工标注快照。对 **当前最新版**冻结集进行 `require_workaround` 的固定文本回放，要求存在可观察的规则差异，但**没有新的已知误报、漏报或基础判定算法漂移**。最近一笔 Owner 回归意见还必须对应这个快照版本和回放证据指纹，并为 `recommend_shadow_review`（只是建议，不是正式规则审批）。
2. **冻结后新人工审核**：从当前最多 400 条活跃 HTTPS 来源中选取不在最新冻结集里的帖子，必须是 **冻结时间之后 Owner 新写入的标签**，且与当前来源 revision 一致。按无查询参数、无锚点的 URL 去重，至少 6 条，正负各至少 2 条，覆盖至少 2 个来源域名。对这批新帖子独立计算原有基础规则和严格规则，不能出现已知新增误报或漏报。

“新人工审核”仅为新的 **帖子级人工分类**：同一人跨两个站点发帖仍可能被算作两个来源，不能声明用户独立性或实际需求已证明。人工标签、帖子发布时间、URL 都不能单独证明作者身份。没有标注 `at` 或早于冻结时间的旧标注不计入新审核；版本变更、撤销分类和来源编辑立即使证据失效。

## 上线安全链路

既有 `releasePreflight` 增加 `frozenRegressionReviewed`，并将最新冻结回放指纹、人工意见以及新增人工审核数据的指纹加入发布证据哈希。`changeProductionRule(action=release)` 在已有验收、来源级签收后也再次计算冻结门槛；任何实际来源数据变化都可能使旧发布前验收哈希失效并阻止灰度。**回滚不受本门槛阻碍**。

注意：当下一次重新冻结样本后，历史新审核帖子可能被纳入新冻结集，因此需要相对于**新的冻结时间**再获得新审核；这是有意设计的“新证据”条件，不通过循环复制旧标签进行补足。

## 版本趋势避免误导

`GET /api/discovery/regression-suite/trend`（仅 Owner）返回：
- 最多20个冻结版本各自的样本大小、正负例、域名数、样本内基础规则和候选规则表现；
- 对比当前同一版本的两种离线规则，基于**相同冻结文本与人工标签**；
- 最新版本的发布门槛状态、阻塞理由、新增人工审核数、证据摘要。

不同冻结版本的数据分布和人工选择可能不同，除非指纹一致，否则 `comparableWithPrevious=false`，**不能把不同样本的准确率差值解释为算法提升**。界面按离散版本记录展示，不绘制暗示可比较的连续准确率折线。

`GET /api/discovery/regression-suite/release-gate` 返回最新只读发布条件和证据指纹；同样经过既有 Owner 认证。所有 JSON 响应只包括样本摘要和最多15条变化示例，不包含冻结集的完整历史原帖正文。原文仍保存在本地 SQLite，并随私人研究数据库一起备份；请勿公开分享数据库。

## 测试与验收

Node 测试使用隔离 SQLite 创建 25 条冻结正反例，再另行人工标注6条冻结后新帖子，覆盖完整合法链路。验证：缺少冻结集/意见/新证据阻断、不同来源和正反例要求、版本编辑后旧证据失效、新证据回归阻断、不同冻结版本不可直接比较、生产发布门槛与原有回滚兼容。真实 HTTP 和 Chromium 验证 Owner 鉴权、面板空状态和只读输出。

真实生产版本和实际统计仍需独立部署校验和 Owner 阅读原始内容。自动化测试全为合成帖子，不代表上线后误报率或准确率已经提高。
